## 1. 产品背景与定位

### 1.1 背景

随着 AI Agent 在复杂任务链路中的广泛应用，Agent 执行失败后的诊断成本居高不下。传统评测系统只能回答"任务是否通过"或"发生了什么"，难以回答"哪一步出了问题、为什么出问题、如何以最小代价修复"。最新研究（如 Causal Agent Replay）指出，仅靠对话日志的模式匹配无法进行稳健的反事实推理，必须通过主动干预来验证某一步是否真为根因。

### 1.2 定位

TracePilot 是一个基于受控反事实实验的智能体（Agent）故障归因与最小修复验证平台。相比普通评测系统，TracePilot 不仅评估 Agent 在任务链路中的完成情况，还构建执行轨迹的因果模型，通过人工干预模拟反事实场景，精确定位失败根因并验证修复效果。

### 1.3 差异化

| 对比项 | 传统 Agent 沙盒测试 / 简单输出评估 | TracePilot |
|--------|----------------------------------|------------|
| 能回答的问题 | 发生了什么、任务是否通过 | 哪一步出了问题、改变该步结果是否恢复成功 |
| 分析方式 | 日志模式匹配 | 轨迹记录 + 因果干预（反事实实验） |
| 修复验证 | 无或仅建议 | 最小干预搜索 + 重新执行验证修复效果 |
| 证据强度 | 相关性 | 实验统计（置信区间、效应值） |

### 1.4 目标岗位匹配

主要面向 Agent 评测、Agent QA、模型评测、AI 应用测试、AgentOps 等岗位；次匹配 AI 应用开发、Prompt 工程等岗位。项目用于展示设计、实现与验证复杂 Agent 系统的能力，而非仅作为前端演示。

## 2. 目标用户及使用场景

### 2.1 用户角色

| 角色 | 核心诉求 |
|------|----------|
| Agent 开发者 / 评测工程师 | 自动分析并定位 Agent 执行失败的根因，减少调试难度，验证修复方案；在 UI 上查看故障传播路径和实验结果；查看评估报告和性能指标 |
| 评测负责人 | 批量统计多个测试样本的归因准确率、修复有效率等指标，生成报告，评估 Agent 的总体可靠性 |
| 面试官 / 招聘方 | 查看项目真实运行成果、技术创新点和工程质量，评估技术深度与解决问题能力 |

### 2.2 典型使用场景

1. **失败诊断**：开发者提交一个失败任务，系统自动执行 Agent、采集轨迹并定位根因步骤。
2. **修复验证**：对定位的根因步骤提出最小修复（修改提示词、替换工具返回值等），验证任务是否恢复成功。
3. **批量评测**：在带人工标注的失败用例集上批量运行归因流程，统计归因准确率、修复成功率、诊断成本。
4. **版本对比**：对比不同算法版本（如启用/不启用故障注入、置信度门限）的指标差异。
5. **成果展示**：在作品集中展示可交互的故障传播 DAG 截图和评测数据。

## 3. 用户痛点与产品价值

### 3.1 用户痛点

| 痛点 | 说明 |
|------|------|
| 根因难定位 | 传统方法只能指出任务失败，难以定位"哪一步出了问题" |
| 修复无验证 | 修复建议缺乏实验证据，无法证明修复确实恢复正确执行 |
| 归因不可信 | 单次日志模式匹配无法进行稳健的反事实推理 |
| 评测无金标准 | 缺少带真实根因标注的测试集，归因准确率无法量化 |
| 诊断成本失控 | 反复全量重跑实验消耗大量 API Token，缺乏成本控制与剪枝 |

### 3.2 产品价值

- 在复杂任务链路中精确定位 Agent 失败原因，并证明经最小干预的修复措施确实能恢复正确执行；
- 提供对因果关系的严格审视，为 AI 系统的可靠性和可解释性提供证据；
- 通过故障注入构造带金标准标注的测试集，使归因准确率可量化、可对比；
- 通过置信度评估、剪枝与成本监测，使诊断过程可控、可审计。

## 4. 核心用户操作流程

### 4.1 端到端主流程（规划）

```
创建任务 → Agent执行 → Trace采集 → DAG依赖分析 → 故障定位 → 反事实干预 → 最小修复验证 → 评测报告
```

### 4.2 各核心模块的输入 / 处理 / 输出（规划）

| 模块 | 输入 | 处理 | 输出 |
|------|------|------|------|
| 创建任务 | 任务指令、Agent 脚本/配置、工具定义、测试输入 | 校验任务配置，登记测试用例与预期目标，生成任务 ID | 就绪的任务实例（含预期输出、元数据） |
| Agent 执行 | 任务实例 | 由 LangGraph 调度执行：规划、工具调用、Skill、RAG 集成 | 每轮执行记录（输入、输出、CoT、工具调用与结果） |
| Trace 采集 | Agent 执行过程的每轮记录 | 按 Trace Schema 标准化并持久化为 JSON（兼容 ATIF 或自定义 schema） | trace.json（含每步输入/输出/推理链/工具调用/上下文快照） |
| DAG 依赖分析 | trace.json | 解析步骤间依赖（串行、并行、条件分支），构建有向无环图；提取图结构依赖关系 | 执行 DAG（邻接列表/图对象），支持后续定位与可视化 |
| 故障定位 | DAG + 失败结果 | 运行根因搜索算法（遍历/启发式，结合剪枝），在候选步骤上执行干预并比较结果；输出候选根因列表及置信度 | 候选根因列表（含排序、效应值与置信区间） |
| 反事实干预 | 候选根因 + 干预配置 | 在指定节点插入"假设结果"或"固定输出"（do 操作），重新触发后续节点 | 干预后执行结果（与原结果对比） |
| 最小修复验证 | 根因定位结果 | 搜索修改该步骤或相关上下文的最小变动（提示词改动、工具选择变更、注入正确返回值等），反复执行验证失败是否消失 | 补救指令/改进建议 + 修复验证结果（成功/失败、干预步数） |
| 评测报告 | 测试集真值 + 全部实验结果 | 统计归因准确率（Top-1/Top-3）、修复成功率、误归因率、平均诊断成本、运行时间；生成对比报告 | 评测报告（JSON/CSV/PDF），含图表与版本对比 |

### 4.3 系统交互流程（规划，依据《总方案》六）

用户上传测试任务（Agent 脚本、工具定义、测试输入等）→ 后端触发 Agent 执行并收集 Trace → 依次运行归因算法生成候选根因及修复方案 → 前端展示失败过程 DAG、每步干预效果、统计指标和最终报告。

## 5. 产品功能模块与优先级

### 5.1 功能模块清单（规划）

| 优先级 | 模块 | 说明 |
|--------|------|------|
| P0 | Agent 执行引擎 | LangGraph 调度：规划、工具调用、Skill、RAG 集成；文件读写、SQLite 数据库接口 |
| P0 | Trace 采集 | 采集每轮输入/输出/推理链/工具调用/工具结果，形成标准化轨迹记录 |
| P0 | 依赖建模（DAG） | 将执行轨迹结构化为因果图，捕捉串行、并行、条件分支依赖 |
| P0 | 根因搜索 | 基于轨迹因果图，在不同时间点执行"改变决策"操作并比较结果 |
| P0 | 最小修复生成 | 定位根因后搜索最小变动并反复验证，输出补救指令或改进建议 |
| P0 | 反事实干预接口 | 在指定节点插入"假设结果"或"固定输出"，重新触发后续节点 |
| P0 | 故障注入与自动测试 | 在关键决策点人工插入错误信息，构造带金标准标注的失败场景 |
| P1 | 置信度评估 | 统计/重采样方法度量归因和修复可信度（置信区间、Shapley 分配） |
| P1 | 门禁控制 | 对置信度过低的归因结果拦截（不确定性感知门控） |
| P1 | 评测指标统计 | 自动计算归因准确率、修复成功率、误归因率、平均诊断成本等 |
| P1 | 故障传播可视化 | 前端 DAG 展示，标注每步输入/输出/故障信息，支持干预前后对比 |
| P1 | 实验管理 | 横向管理评测实验的配置、输入、输出、指标、成本，支持版本对比 |
| P2 | 数据存储 | SQLite/本地文件存储轨迹记录与实验结果，保留样本与版本迭代记录 |
| P2 | 报告导出 | 导出报告（JSON/CSV/PDF） |
| P2 | 性能监控 | 响应时间、成功率、异常信息统计与面板展示 |
| P2 | 成本监测与优化 | 实时统计 Token 消耗；调度、缓存、剪枝降低成本 |
| P2 | CI/CD 与部署 | GitHub Actions 持续集成；Docker 一键部署脚本 |
| P2 | 安全策略 | API Key 保护、有害输出过滤、上下文脏数据审查 |

### 5.2 系统分层（规划，依据《总方案》六）

1. **Agent 执行层**：LangGraph 调度；文件读写与数据库接口；故障注入接口；反射/记忆/安全模块钩子。
2. **轨迹与因果建模层**：Trace Schema 定义；DAG 构建；依赖分析；干预接口。
3. **故障归因实验层**：根因搜索算法；修复验证；置信度计算；评测指标计算。
4. **交付与监控层**：FastAPI 后端；React 前端（任务配置、执行监控、Trace DAG 可视化、归因报告、指标仪表盘）；数据存储；CI/CD 与自动化测试；实验管理。

## 7. 7 个创新方向及实验验证要求

> 以下 7 个创新方向均需设计并运行可证伪实验；任何创新宣称都需实验证实，否则不计入最终成果。当前均为规划，未开展实验、无实验结果。

| # | 创新方向 | 内容概要（规划） | 实验验证要求（规划） |
|---|----------|------------------|----------------------|
| 1 | 因果轨迹代数 Causal Trace Algebra | 在轨迹 DAG 上形式化定义干预算子（固定某步操作、将工具返回置为特定值等） | 给出有明确因果关系的合成任务（可控因素金标准模型），验证轨迹代数能正确表示并对比实验结果 |
| 2 | 最小充分干预搜索 Minimal Sufficient Intervention | 在根因候选周围搜索最小干预集（调整 prompt、替换工具输出等），模拟验证是否成功 | 构造失败任务（如带误导性文档的 QA 任务），平台输出的干预应最小且能恢复正确结果；记录"修复前后结果差距"与"干预步数"指标 |
| 3 | 不确定性感知门禁 Uncertainty-Aware Gatekeeping | 归因结果施加置信度门限；反事实干预显著改善（如 CI 不含 0）才认定有效根因 | 对每个候选根因多次反事实重放，记录置信区间；设置门限（如 95% CI）观察归因稳定性；监测漏诊率与误诊率 |
| 4 | 因果影响剪枝 Causal Effect Pruning | 节点干预后效应接近 0 时剪掉其下游分支搜索，降低成本 | 在多噪声步骤模型中对比剪枝前后归因效率；对比未剪枝情况的 API 调用次数与准确率 |
| 5 | 故障注入与自动测试 Fault Injection & Test Generation | 在任一轨迹步骤或 RAG 结果注入故障（语义噪声、工具超时、上下文垃圾），记录注入位置作为金标准根因 | 设计若干故障场景（SQL 参数注入异常值、工具返回错误数据等），比较归因准确率与修复建议有效性，统计"注入到定位的平均时间"和"漏诊率" |
| 6 | 根因准确率评估 Root-Cause Accuracy Metrics | 以标注真值与平台候选根因匹配，计算 Top-1 准确率、Top-3 覆盖率、误归因率、修复成功率、平均 Token 成本 | 在固定测试集上统计指标并输出图表；与基线方法（随机猜测、启发式模式匹配）对比 |
| 7 | 失败传播路径可视化 Failure Propagation Visualization | 将执行过程渲染为可交互 DAG，标注"假设被修复时会如何"（修复前后分支对比） | 前端演示完成一次故障归因图形报告，至少包含：故障步骤前后状态、每步输出与工具调用结果、干预方案、效应值/置信区间；经多轮演示与反馈验证清晰度 |

通用要求：所有创新点实验需可复现脚本和自动化统计；故障注入实验需预先生成含标注的 JSON 任务集并批量运行归因流程；可视化功能需包含标准示例数据文件以便 Demo 实时展示。

## 8. 功能性与非功能性需求

### 8.1 功能性需求（规划）

| 编号 | 需求 | 说明 |
|------|------|------|
| F-1 | 任务提交与管理 | 用户提交任务（Agent 脚本、工具定义、测试输入、预期目标），平台登记并管理任务 |
| F-2 | Agent 执行与 Trace 采集 | 自动执行 Agent，按 Trace Schema 采集每轮输入/输出/CoT/工具调用与结果，保存 JSON |
| F-3 | DAG 构建与依赖分析 | 解析步骤依赖（串行、并行、分支），构建 DAG 并支持查询 |
| F-4 | 干预执行 | 指定节点注入假设结果/固定输出，重新运行后续节点，输出干预前后对比 |
| F-5 | 根因搜索与最小修复 | 遍历/启发式搜索候选步骤，输出候选根因排序与最小修复建议，并验证修复效果 |
| F-6 | 置信度与门禁 | 多次干预获得成功/失败概率分布，计算置信区间；对低置信度结果拦截 |
| F-7 | 故障注入 | 参数化在第 N 步注入错误（返回空数据、异常、垃圾上下文），记录注入点作为金标准 |
| F-8 | 评测指标统计 | 计算 Top-1/Top-3、修复成功率、误归因率、平均诊断成本、运行时间，支持版本对比 |
| F-9 | 可视化与报告 | React 前端展示 DAG、故障高亮、干预对比、指标仪表盘；导出 JSON/CSV/PDF 报告 |
| F-10 | API 服务 | FastAPI 提供任务提交、结果查询、报告获取接口，附完整 API 文档 |

### 8.2 非功能性需求（规划）

| 类别 | 要求 |
|------|------|
| 可靠性 | 常见测试在合理时间内完成，评估过程可可靠重现（参照 Who&When 等基准执行时长尺度）；归因结论须附置信区间而非单次结果 |
| 可解释性 | 归因结果明确说明"在当前实验设置下该步改变可显著改善结果"，不宣称绝对真理 |
| 性能 | 无明确数值指标（待后续设定），保证诊断全流程可批量化自动执行 |
| 安全性 | API Key 严禁公开；内置违规检测与过滤规则；上下文审查防脏数据注入 |
| 可维护性 | 模块化四层架构；核心模块单元测试与集成测试；文档规范（PROJECT_STATE.md、DECISIONS.md） |
| 可部署性 | Docker/虚拟环境支持一键部署，CI/CD（GitHub Actions）自动运行测试 |
| 成本可控 | 实时统计 Token 消耗；利用缓存/闲时折扣、并发限制控制成本 |
| 兼容性 | Trace Schema 兼容 ATIF 或自定义 schema；国内网络环境下可访问的模型服务 |

## 10. 产品成功指标

> 以下为规划中的目标指标，当前无任何实验数据。基线参考：《总方案》引用的研究显示，模式匹配基线在 Who&When 基准上步骤级准确率仅约 14%（参考文献 [7][8]，待核对）。

| 指标 | 定义 | 目标（规划） |
|------|------|--------------|
| RootCause Top-1 准确率 | 第一个候选根因是否正确 | 显著超越基线（模式匹配约 14%） |
| RootCause Top-3 覆盖率 | 真根因是否出现在前 3 个候选中 | 显著超越基线 |
| Repair Success Rate | 推荐修复措施是否使任务成功 | 显著超越基线 |
| 误归因率 False Positive | 标为根因但实际无效的比例 | 尽可能低，纳入报告 |
| 平均诊断成本 | 单次故障诊断消耗的 API Token/美元 | 报告并对比剪枝/门禁开关前后的差异 |
| 运行时间 | 完成一次故障定位与验证所需时间 | 合理时间范围内完成 |
| 功能完成度 | 20 项能力自动化验证通过率 | 100%（至少 L2，核心能力 L3） |
| 实验可复现性 | 7 个创新实验均有可复现脚本与统计 | 100% |
| 工程交付 | CI 绿色通过、Demo 可访问 | 达成（见第 12 节） |

## 11. 主要风险及限制

| 风险/限制 | 说明 | 应对（规划） |
|-----------|------|--------------|
| 归因的因果边界 | 步骤 A 修改后失败概率降低，不意味 A 是唯一根因（下游可能交互影响）；归因只表示"当前实验设置下该步改变可显著改善结果" | 文档与报告中明确说明边界；不宣称绝对真理 |
| 多步骤相互作用 | 多个步骤共同导致失败（如两步同时出错才失败） | 使用 Shapley 等方法分配贡献；最小修复先搜单步，无法单步完成再考虑双步组合 |
| 模型随机性 | LLM 温度采样导致相同干预结果分布不同 | 多次重复干预实验，统计结果分布（均值/置信区间），报告置信度范围而非单次结果 |
| 国内网络与模型可用性 | Claude 在中国大陆无法官方使用（Anthropic 地区政策） | 优选 DeepSeek 系列；备选 Qwen 系列；不依赖需 VPN 的服务 |
| API 成本 | 反复反事实重放消耗大量 Token | 实时统计消耗；利用缓存/闲时折扣与并发额度；剪枝策略；必要时并发限制 |
| 开发回滚风险 | 架构修改可能导致系统不稳定 | Git 分支及时提交；失败功能回滚上一稳定版本；决策记录于 DECISIONS.md |
| 信息丢失风险 | 会话断开或模型切换导致上下文丢失 | PROJECT_STATE.md 记录进度；定期备份依赖列表与数据库快照 |
| 待确认事项（来自《总方案》十三） | 部分截图内容不可直接读取；智能体开发工具实际可用模型版本 ID、工具参数格式、部署环境与安全配置待查证 | 开发中逐一核对后更新本 PRD |
