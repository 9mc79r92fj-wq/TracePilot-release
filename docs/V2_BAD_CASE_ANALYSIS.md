# TracePilot V2 · Bad Case 分析（AgentRx 真实对照实验）

本文件分析 `docs/V2_BENCHMARK_REPORT.md` 中 25 条真实案例的失败样本。所有数字都从
`data/v2_experiments/benchmark_rootcause_results.json`（运行时原始产物）重新统计，未做任何人工修饰。

数据：AgentRx 公开 GitHub 子集 test split，按 case_id 排序取前 14 条 tau + 前 11 条 magentic；模型 `deepseek-flash`。

## 1. 总体误差账

| 方法 | Top-1 命中 | 误差步 ±1 | 偏早 | 偏晚 | 未给出 |
|---|---:|---:|---:|---:|---:|
| Baseline B（确定性规则） | 1/25 | 1 | 15 | 6 | 2 |
| Baseline A（LLM 直接诊断） | 8/25 | 2 | 8 | 7 | 0 |
| TracePilot V2（规则+证据+LLM） | 5/25 | 3 | 9 | 8 | 0 |

交叉情况：A 与 V2 同时命中 5 条；仅 A 命中 3 条；仅 V2 命中 0 条；都未命中 17 条。

**关键结论：V2 的误差并不系统性偏向“下游症状”（偏早 9 / 偏晚 8），失败主要是“落在同一条长轨迹的其它
合理异常步”上。** 这意味着问题不在“最早根因”这一启发式方向，而在**归因粒度**：AgentRx 的标签是
“标注者认定的那一次具体失败实例”，不一定等于轨迹中的最早异常。

## 2. 误差类型分类

### E1 标签粒度冲突：AgentRx 标注“具体失败实例”，V2 输出“最早异常”（主导类型）

**代表案例 tau-104**（58 步，标签 57，V2 预测 21，A 预测 2）
- 标签理由：助手误读工具输出，**在最后一步**没有把已取消订单的物流单号告知用户。
- V2 理由：把步骤 21“将已送达订单误判为无法取消”当根因，并明确写“后续步骤均为症状”。
- 分析：步骤 21 确实是更早的真实异常，但 AgentRx 的根因是该轨迹**被标注的那次失败**（漏答单号）。
  V2 的“最早根因”Prompt 与 AgentRx 的标注定义存在语义错位。此类案例无法靠调 Prompt 修复，
  需要把标签定义（失败实例 vs 最早异常）显式建模为两种输出并分别评测。

### E2 过度归因到更早的无关政策违规

**代表案例 tau-38**（46 步，标签 37，V2 预测 3，A 预测 21）
- 标签理由：助手没有从工具输出中发现“最便宜商品不可用”，导致选错商品。
- V2 理由：把步骤 3“未认证就回答支付问题”当作根因，并称后续均为连锁症状。
- 分析：步骤 3 是早期政策违规，但与最终失败无因果链；V2 的规则/DAG 信号把“显式违规”权重放得过高，
  模型顺着这个信号做了一个自洽但错误的因果故事。这是**规则先验导致的假因果**。

### E3 相邻步骤/归因边界偏差

**代表案例 magentic-16d825ff-1623-4176-a5b5-42e0f5c2b0ac**（130 步，标签 5，V2 预测 4，A 预测 5）
- 标签：WebSurfer 无法检索到指定日期的到达时间，Orchestrator 后续反复邮件（错策略）。
- V2：指向步骤 4 的 Orchestrator 指令（要求检索不存在的数据）。
- 分析：4 与 5 是同一因果链上的相邻两步（下达不可完成指令 → 检索失败）。对长轨迹而言，
  标注者取的是“执行侧失败”，V2 取的是“计划侧失败”，两者都成立但粒度不同。
  这类误差在 ±1 容忍下应视为部分正确，但严格 Top-1 计为错误。

### E4 对确定性候选的锚定（少数但全错）

- V2 预测步骤恰好等于某个确定性候选的案例：**4/25，且这 4 次全部错误**。
- 说明规则候选目前更多是“噪音源”而不是有效先验；一旦模型完全采纳候选，几乎必错。
- 反例：21/25 案例中 V2 没有照抄候选，说明模型并非被候选强制锚定，但候选也几乎没提供正确信号。

### E5 类别体系归因差异

**代表案例 tau-98**（38 步，标签 21，V2 预测 15，A 预测 21）
- 标签类别 `Intent Plan Misalignment`（应先改地址再改商品，顺序错导致订单锁定）。
- V2 类别判为 `Invalid Invocation`（把步骤 15 对 pending 订单调用 exchange 当作根因），
  即使步骤判断正确，类别标签也会错；类别集合来自 AgentRx 人工标注，存在多标签/近义合并问题
  （`rootcause_v2._normalize_category` 只做大小写与少量近义词归一）。

## 4. Top-3 优势的来源（必须如实说明）

表面上 V2 的 Top-3（0.40）高于 A（0.32），但存在**结构性不对等**：

- Baseline A 的 Prompt 只要求输出一个 `root_cause_step`，其 `top3_steps` 长度**恒为 1**（25/25）；
  Top-3 指标对 A 而言退化为 Top-1。
- V2 的 Prompt 额外要求输出最多 3 个候选步，`top3_steps` 长度恒为 3（25/25）。

因此“Top-3 提升”部分来自**输出格式差异**，不能作为架构优势的独立证据。V2-only 的 Top-3 命中 4 条
（tau-28、tau-39、magentic-42576abe…、magentic-5f982798…），但它们的 Top-1 全部未命中；
若给 A 同等的多候选预算，差距可能消失。**这组对照应在报告中按“不具备统计显著性”处理。**

## 5. 已尝试与未尝试的改进

已尝试（同一 25 条案例，见 `iterations` 字段）：

| 版本 | 改动 | Top-1 | Top-3 | Category Acc |
|---|---|---:|---:|---:|
| v2.0 | 提供候选与类别提示 | 0.20 | 0.32 | 0.16 |
| v2.1 | 强调最早根因、提示候选可能含症状、要求独立判断 | 0.20 | 0.40 | 0.20 |

- v2.1 在**同一批案例上**修改 Prompt，属于事后调参，**没有独立验证集**，存在过拟合风险；
  报告不把 0.20→0.20 / 0.32→0.40 当作泛化提升，只当作“该 Prompt 在本批数据上的版本记录”。

未尝试（受时间与预算约束，如实记录）：

1. 标签粒度双输出（失败实例 / 最早异常）分别评测；
2. 多候选边界的边界 case 自动识别（相邻步合并后再评）；
3. 多次采样 + 投票（成本 ×3 以上，预算不允许）；
4. 类别体系映射表人工对齐；
5. 独立 dev split 调 Prompt、test split 只评一次（本轮 dev split 未参与真实调用）。

## 6. 结论

1. V2 在当前样本上**没有超过 Baseline A 的 Top-1**（0.20 vs 0.32），不能宣称架构更优；
2. V2 的类别 Macro-F1 略高（0.0926 vs 0.0873），但样本仅 25 条、类别极不均衡，**不足以支撑优势结论**；
3. 主要失效来自标签粒度语义错位（E1）与规则先验误导（E2/E4），而不是单纯的“找症状”；
4. 任何“V2 优于直接 LLM 诊断”的表述在本实验数据下都不成立，后续需要独立验证集与标签粒度对齐后重测。
